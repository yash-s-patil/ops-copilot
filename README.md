# Ops Copilot

A reference deployment of an MCP server and an agent on private Azure.

A support engineer opens a ticket; an agent investigates it across orders, customers,
policies and runbooks and proposes a fix. The agent holds no rights over business data:
it acts with the signed-in engineer's delegated identity, and every write needs a human
approval bound to the exact arguments.

**Status:** under construction. The MCP server, the payments worker, the agent and the web
application run locally with a scripted model. The Azure deployment follows.

## Quick start

Requires Docker, [uv](https://docs.astral.sh/uv/), Node 24 with pnpm, Terraform 1.17, [tflint](https://github.com/terraform-linters/tflint) and GNU Make.

```
make install  # install the locked toolchain into .venv
make dev      # build and start local PostgreSQL, Azurite, the MCP server, the agent, the payments worker, the local stand-ins and the web application at http://localhost:3000
make lint     # formatting, lint rules, secret scan on commit, strict type checking
make migrate  # apply database migrations locally
make seed     # load the deterministic demo data and upload the policy documents (replaces what is there)
make test     # Python unit tests with coverage
make test-integration  # tests against local PostgreSQL and Azurite
make test-web # web unit tests, then the browser tests (Playwright)
```

Run `make help` for every target. After pulling a change to the local database or storage setup, run `make dev-reset`.

`make dev` serves the MCP server at `http://127.0.0.1:8000/mcp`, with `/healthz` and `/readyz` beside it. It publishes six read tools, two write tools, four resources and two prompts. Every request needs a bearer token issued for this server; without one the answer is `401` and a pointer to `/.well-known/oauth-protected-resource/mcp`. Locally the sign-in service is replaced by a signing key that `make env` generates into `.env`: `make token WHO=priya` prints a token for one of the five demo users (`priya`, `rohan`, `arjun`, `kavita`, `sam`), and `make smoke` checks that each is shown only their own tools, and that the agent refuses a token meant for the MCP server. A server started with that local sign-in refuses to run outside `ENVIRONMENT=local`.

Every tool call that reaches a tool, whether it succeeds, fails or is refused for lack of permission, appends one row to `audit.audit_log` and writes one log line with the same fields. Arguments are recorded with email addresses and phone numbers replaced by a hash and other text cut to 200 characters. Each row carries the hash of the row before it, so a changed or removed row is detectable: `make verify-audit` checks the chain. If the row cannot be written, the caller gets an error and not the result. Each person may make 60 requests a minute with a burst of 20; the next one is answered `RATE_LIMITED` with the seconds to wait, and is logged but not added to the audit log.

The two write tools, `update_ticket` and `issue_refund`, change nothing when called. A call is checked (input, permission, and for a refund the refund policy in `services/refund_policy.py`), recorded as a pending action, and answered with `approval_required`, the action's id and the hash of its exact arguments. A refund up to INR 5,000 waits 15 minutes for its requester's confirmation; a larger one waits 24 hours for a supervisor. Repeating a call with the same `idempotency_key` returns the same action; the same key with different arguments is `IDEMPOTENCY_CONFLICT`. A person decides through routes beside the MCP endpoint, which no tool can reach: `GET /approvals` and `GET /approvals/{id}` show what waits, `POST /approvals/{id}/approve` takes the `args_hash` the person was shown, `POST /approvals/{id}/reject` takes a reason, and `POST /approvals/{id}/token` gives the requester a fresh token for an approved action. They need the same bearer token as `/mcp`. A refund at or under the limit is confirmed by its requester; a larger one by a supervisor who is not the requester, and that approval hands nobody a token until the requester asks for one. An approval token is a signed ES256 token naming the requester, the approver, the action and the hash of its arguments; it lasts 120 seconds. Locally it is signed with a key that `make env` generates; in Azure the key stays in Key Vault. To carry an approved action out, the agent calls the same tool again with the same arguments, the same `idempotency_key` and the token. In one database transaction the server takes the action (so a second call cannot), records the token's id as used, checks the rules again as they stand at that moment, writes the change and writes the audit row. A refund is written together with a row in the outbox, the queue from which a separate payments worker will pay it; this server never calls a payment service. If the rules now refuse the write, nothing is changed and the action is marked failed. Repeating a call that was carried out returns the stored result and writes nothing.

An approved refund is a decision; paying it is a separate step done by a separate program. `payments-worker` (`services/payments/`) has no HTTP ingress. Every 2 seconds it takes the outbox rows that are due, each in its own transaction that also holds the row, so two workers never take the same one. For a new row it calls the payment service with the header `Idempotency-Key: refund-<id>` and moves the refund to `sent_to_payments`; for a submitted row it asks for the result and moves the refund to `paid` or `failed`, leaves a note on the ticket in the name `Payments`, and appends an audit row (`submit`, `settle`). A provider that does not answer is retried with a growing pause, 5 times in all, after which the refund is `failed` with `payment_service_unavailable`. Nobody knows then whether the provider paid it, so such a refund still counts against its order: no second refund can take its place, and the way forward is Retry payment under the same key. If the worker stops between the provider's answer and the commit, the row is as it was and the next attempt repeats the call under the same key, so a refund is never paid twice. The worker connects to PostgreSQL as `payments_worker`, a role that can change four payment columns of a refund and nothing else about it, and cannot read a customer, an order or a ticket. What it tells the provider is an order number, an amount and a currency.

`payments-sim` stands in for a payment provider; no money moves. It answers `processing` for 3 seconds and then `succeeded`, returns the first result for a repeated key, and accepts only a token issued for it that carries the app role `Payments.Submit`: in Azure an app-only token of the worker's managed identity, locally a token signed with a key of the worker's own that `make env` generates. It refuses to start when `ENVIRONMENT` is `prod`. A real provider is one adapter behind `ports/payments.py`.

A refund whose payment failed is sent round again with `POST /refunds/{id}/retry` on the MCP server, the route behind the Retry payment button. It needs `refunds.request` and a refund the caller can see; no tool can reach it. In one transaction, with the order's refunds held still, it checks that no other request on the order is waiting, that the refund still fits beside the refunds made since, and that those have not pushed a self-approved refund over the limit a supervisor guards; then it makes it `approved` again, writes a new outbox row and the audit row (`retry`). The amount, the order and the idempotency key do not change, so a retry can neither pay more nor pay twice.

The agent (`services/agent/`, served at `http://127.0.0.1:8001`) runs investigations and holds no rights over business data. It has its own database, `copilot`, with a role and a password of its own, and no role in `meridian`, the storage account or the search index: tests connect as its role and are refused, and try its password on every other role. Everything it reads or asks to change goes through the MCP server with the signed-in engineer's authority. The web application gives it a token issued for the agent (token A). The MCP server refuses that token, so the agent exchanges it for one issued for the MCP server that names the same person (token B). This is the OAuth on-behalf-of exchange; in Azure the agent proves itself to Entra with its managed identity and holds no secret. Locally `dev-issuer` (`infra/local/issuer/`) stands in for Entra's token endpoint, and is the only program that holds the key that signs people in. Token B is kept in memory until five minutes before it expires. When the MCP server answers `401` the agent exchanges again and repeats that one request once; a second `401` pauses the run as `reauth_required` until its owner signs in again. When the server answers `RATE_LIMITED` during a run, the run waits the seconds the answer names (5 at most, three times a request) and asks again; a screen read is answered `429` at once and the browser waits instead. No token is written to a run's saved state, its events or the log.

A run is a LangGraph graph: `prepare` (list the tools this person may use, load the reference texts and the procedure), `reason` (one model call), `gate`, `tools` (reads, run together), `propose` (write tools called without an approval, which only records the request), `await_approval`, `execute`, `reply`. `await_approval` is an interrupt: the run's state is saved in PostgreSQL by the LangGraph checkpointer, and the run goes on when people have decided, in whichever process its owner next reaches. A process holds a lease on a run while it works and renews it; a run whose process died is picked up from its last saved step when its owner reconnects. Ordinary code, not the model, enforces the limits: 15 tool calls, 8 model turns, 60,000 tokens and 120 seconds a run (a tool result is counted by its length before the model reads it); a canary string in the system prompt that stops the run if it appears in an answer or an argument; a change is dropped unless it cites a tool result that came back whole, and a refund unless its amount follows from the order it cites and the policy; a reply draft with anyone's contact details but the customer's is withheld. Tool results reach the model between marker lines that say they are data, with the markers escaped inside. These lower the odds of a wrong request. What makes a wrong request harmless is the MCP server: its own policy check, and the approval no tool can give.

`POST /api/runs` starts a run and `GET /api/runs/{id}/events` streams it as server-sent events. Each event is stored with a sequence number before it is sent, so a browser that reconnects with `Last-Event-ID` misses nothing. `POST /api/runs/{id}/actions/{action_id}/approve` takes the `args_hash` of the card the person saw and passes their decision to the MCP server; a supervisor decides with `/api/approvals/{id}/approve`, and the requester carries an approved change out with `/api/approvals/{id}/execute`. `GET /api/tickets` and `GET /api/tickets/{id}` give the screens their data by calling the same tools with the caller's token, so masking, row-level security, caps and audit apply as in a run. `POST /api/tickets/{id}/resolve` is the Resolve button: request, approval and execution, each audited. It takes an `Idempotency-Key` header that names the click, so a repeat goes on from where the first attempt stopped. `GET /api/me` reports the caller's permissions as the MCP server grants them; the agent keeps no copy of the role table. Routes under `/api/admin` need the administrator's role and return the admin projection: event types, tools, timings, sizes and codes, with no message, model text, step summary or free-text argument.

Locally the model is replaced by a scripted one (`LLM_PROVIDER=scripted`) that follows the server's `investigate_order` procedure by fixed rules, so the whole flow runs without a model. It says nothing about how a real model behaves and is refused in `prod`. `make token WHO=priya` prints token A; `make token WHO=priya FOR=mcp` prints a token for calling the MCP server directly.

The web application (`apps/web/`, Next.js) is served at `http://localhost:3000`; open it as `localhost`, not `127.0.0.1`. The browser talks only to the web application's own server. Calls for data go to `/api/bff/*`, where the server adds the signed-in person's token and passes on a fixed list of the agent's routes, with only the query names and headers that list allows; anything else is `404`, and a change that does not come from one of the application's own pages is `403`. The token is kept in an encrypted, httpOnly session cookie and is never handed to code in the browser. Locally, sign-in is a list of the five demo users: the server asks `dev-issuer` for that person's token, and a web application started with that sign-in refuses to run outside `ENVIRONMENT=local`. Every page is sent with a Content-Security-Policy that carries a nonce made for that request, so only the application's own scripts run.

Every call the MCP server makes to PostgreSQL or Blob storage goes through a guard for that backend. It allows at most 20 calls in flight, gives each attempt a time limit, and retries a read up to twice, with a random and growing pause, when the failure is a lost connection, a `429` or a `5xx`. A write is never retried. After 5 failures in 30 seconds the guard's circuit breaker opens: calls are refused at once with `BACKEND_UNAVAILABLE` for 20 seconds, then one probe is let through, and its success closes the breaker. The breaker is kept per process, so each replica learns for itself. The resource `meridian://server/health`, readable by anyone with a role, reports each backend as `ok`, `recovering` or `unavailable` and lists the tools that cannot be relied on.

## Layout

| Path | Contents |
|---|---|
| `config/` | `limits.yaml` (every cap, timeout and threshold) and `pricing.yaml` |
| `packages/opscp_common/` | Code shared by the services |
| `services/mcp/` | The MCP server: migrations, the tools, resources and prompts, the approval and retry routes, and its image |
| `services/agent/` | The agent: the graph, the token and MCP clients, guardrails, run events, the HTTP API, migrations for its own database, and its image |
| `services/payments/` | The payments worker and the payment simulator: one package, one image, two entry points |
| `jobs/seed/` | Loads the demo data and uploads the policy documents |
| `infra/local/` | What stands in for Azure on a laptop: the token issuer, the token and smoke scripts, the database roles |
| `data/` | The runbooks and policy documents the assistant reads |
| `apps/web/` | The web application (Next.js): the inbox, ask and admin screens, sign-in, the routes that pass the browser's calls on to the agent, and its image |
| `infra/terraform/state-bootstrap/` | One-off storage account for Terraform state |
| `.github/workflows/` | Continuous integration |
